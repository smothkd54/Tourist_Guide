# Pushkinskaya Street Tourist Guide — Landmark Recognition System

A tourist landmark identification system for Pushkinskaya Street, Rostov-on-Don, Russia.
Identification runs entirely on your machine — no cloud API. Route planning and map tiles use public OSRM/OpenStreetMap services when online.

## Quick start

### 1. Clone with Git LFS (for images)

```bash
git lfs install
git clone https://github.com/smothkd54/Tourist_Guide.git
cd Tourist_Guide
```

### 2. Install dependencies

Requires Python 3.11 or newer.

```bash
pip install -e ".[dev]"
```

This installs the package in editable mode with all training, testing, and linting dependencies.

For production/Docker (slimmer, no matplotlib/pytest):
```bash
pip install -r requirements-serve.txt
```

### 3. Start the server

```bash
python backend/app.py
```

Open http://localhost:5000/app in your browser.

The dev server binds to `127.0.0.1` by default (not reachable from your LAN). Set `HOST=0.0.0.0` if you explicitly want to expose it. Docker/gunicorn is unaffected and still binds `0.0.0.0`.

### CLI entry points

After `pip install -e ".[dev]"`, these commands are available:

| Command | What it does |
|---------|-------------|
| `pushkinskaya-train` | Fine-tune EfficientNetB0 |
| `pushkinskaya-evaluate` | Generate confusion matrix + metrics |
| `pushkinskaya-predict` | CLI inference on a single image |
| `pushkinskaya-collect` | Organise raw photos into train/val/test splits |
| `pushkinskaya-plan` | Generate a walking route via OSRM |
| `pushkinskaya-preflight` | Verify model + data before starting server |

### Docker

**Quick start (docker-compose):**
```bash
git lfs pull
cp .env.example .env
# Set CORS_ORIGINS and a real METRICS_TOKEN in .env — compose refuses to
# start while METRICS_TOKEN is empty. Generate one with:
#   python -c "import secrets; print(secrets.token_urlsafe(32))"
docker compose up -d
```

This starts:
- **Caddy** (ports 80/443) — reverse proxy with auto-HTTPS via Let's Encrypt
- **web** (port 5000 internal) — Flask + gunicorn backend

**Manual (docker run):**
```bash
git lfs pull
docker build -t pushkinskaya-explorer .
docker run -p 5000:5000 \
  -e CORS_ORIGINS=https://your-domain.com \
  -e METRICS_TOKEN=replace-with-a-long-random-value \
  pushkinskaya-explorer
```

**Swap model without rebuild:**
```bash
python convert_tflite.py && docker compose restart
```

**Environment variables (.env):**

| Variable | Default | Description |
|----------|---------|-------------|
| `HOST` | `127.0.0.1` | Dev server bind address (`python backend/app.py` only) |
| `CORS_ORIGINS` | `http://localhost:*\|http://127.0.0.1:*` | Pipe-delimited allowed origins (exact host, `:*` = any port; matched with anchored patterns) |
| `GUNICORN_WORKERS` | `2` | Number of gunicorn worker processes |
| `MODEL_PATH` | `/app/models/landmark_classifier.tflite` | Path to the TFLite model |
| `LOG_DIR` | `/app/logs` | Directory for log files |
| `METRICS_TOKEN` | *(required by compose)* | `/metrics` requires this value in the `X-Metrics-Token` header. Compose refuses to start without it |

## Android app

`android/` is a native Kotlin/Compose client for the same API: Explore, Detail
(with photo credit), Identify (camera or gallery → `POST /predict`), Routes
(`POST /plan-custom`) and local reminders.

```bat
cd android
gradlew.bat assembleDebug
adb reverse tcp:5000 tcp:5000
adb install -r app\build\outputs\apk\debug\app-debug.apk
```

`adb reverse` maps the phone's `localhost:5000` to the PC, so the debug build
does not need a LAN IP or `HOST=0.0.0.0`. CI builds the APK and runs its unit
tests; launch is verified on the demo phone.

Route reminders use `AlarmManager`; WorkManager is used only for the 6-hour
place-status poll, where a late run is harmless.

## Photo attribution

`data/photo_attribution.json` records the author, licence, licence URL and
source page for every published thumbnail. `scripts/audit_photo_licenses.py`
rebuilds it from the Wikimedia Commons API and fails if any published photo
lacks a free licence or a credit. The API attaches the credit to each landmark
as `photo_attribution`, and both the web UI and the Android detail screen show
it under the photo.

Run the audit in CI (`.github/workflows/photo-audit.yml`), not locally:
Wikimedia is unreachable from the developer's network.

## Deployment

The free-tier plan (Render + Neon) does not survive a network check from
Rostov-on-Don: `render.com`, `api.render.com` and deployed `*.onrender.com`
hosts reset the TLS connection, so the dashboard cannot be reached and a
hosted demo cannot be verified from the venue. Yandex Cloud is reachable but
needs an account and a payment method.

The supervisor demo therefore runs locally: the Flask API on the laptop, the
phone over USB with `adb reverse`, and the web UI at `http://127.0.0.1:5000/`.
This has no external dependency and no cost.

## API reference

| Method | Endpoint              | Body / Params                | Returns                              |
|--------|-----------------------|------------------------------|--------------------------------------|
| GET    | `/`                   | —                            | health check + model status          |
| GET    | `/app`                | —                            | web UI (also `/app/`)                |
| GET    | `/app/static/<path>`  | —                            | self-hosted static assets            |
| GET    | `/favicon.ico`        | —                            | SVG favicon                          |
| GET    | `/landmarks`          | —                            | array of all 46 landmark objects (with `photo_attribution` when a photo is published) |
| GET    | `/landmarks/<id>`     | —                            | single landmark object               |
| GET    | `/nearby`             | `lat`, `lon`, `radius_m`     | landmarks within radius              |
| GET    | `/plan`               | `start`, `minutes`, `visit`  | dynamic walking route via OSRM       |
| POST   | `/plan-custom`        | `{ landmarks, start, optimize? }` | custom walking route via OSRM    |
| GET    | `/route`              | —                            | pre-planned route from `planned_route.json` |
| GET    | `/photo/<id>`         | —                            | thumbnail image for a landmark       |
| GET    | `/photos/available`   | —                            | list of landmark IDs with photos     |
| POST   | `/predict`            | `{ "image": "<base64>" }`    | prediction + landmark info (10 MB max) |
| GET    | `/model/info`         | —                            | model training metadata (404 if absent) |
| GET    | `/metrics`            | —                            | Prometheus metrics (header token when configured) |
| GET    | `/sw.js`              | —                            | service worker script                |

Parameter details:
- `/nearby` — `lat`/`lon` must be finite and in range; `radius_m` is 1–50000 (default 500).
- `/plan` — `minutes` is 15–480 (default 60); `visit` is 0–120 and optional (per-landmark dwell is estimated when omitted). Limited to 30 requests/minute per client.
- `/plan-custom` — `landmarks` is a non-empty list of known landmark ID strings (duplicates are removed); `start` must be one of them; `optimize` must be a boolean.
- `/predict` — JSON body up to 10 MB; base64 or data-URI JPEG/PNG.

Health check returns `503` (not `200`) when the model is missing or is a Git LFS pointer stub.

## Training pipeline

### Step 1 — Collect photos

Place your photos in `data/raw/<landmark_id>/`. Aim for at least 10 photos per landmark.

### Step 2 — Organise splits

```bash
python collect_data.py
```

Splits photos 80% train / 10% val / 10% test. Use `--source PATH` to read from a directory other than `data/raw`.

### Step 3 — Train

```bash
python train.py --epochs-head 10 --epochs-fine 20
```

Options:
```
--batch       INT   batch size (default 32)
--epochs-head INT   phase 1 epochs, head only (default 10)
--epochs-fine INT   phase 2 epochs, fine-tune (default 20)
```

Training uses EfficientNetB0 (pretrained on ImageNet) with two phases:
- **Phase 1**: classification head only (base frozen)
- **Phase 2**: top layers unfrozen, end-to-end fine-tune

After training, `models/model_metadata.json` is written with class count, accuracy, training timestamps, and hyperparameters.

### Model quality (current checkpoint)

Measured on a held-out split that no training image touches, with duplicate and
near-duplicate photos kept inside a single split:

| Metric | Value |
|---|---|
| Classes | 29 (of 46 landmarks; the rest stay browsable but are not camera-recognised) |
| Test accuracy | 60.0% (39/65) |
| Answer precision at the 0.35 threshold | 82% (94% at 0.40) |
| Coverage at 0.35 | 52% of test photos answered |

Known limitation: the classifier has no "not a landmark" class, so it will
confidently guess when pointed at something that is not a listed building. The
API returns the top 5 candidates so the user can correct it.

Two classes (`lashch_revenue_house`, `tkachenko_revenue_house`) survive only in
the training split — Wikimedia Commons has no further free-licensed photos — so
they are masked out of predictions rather than returned unvalidated.

### Step 4 — Evaluate

```bash
python evaluate.py                 # add --model PATH to evaluate a different .keras file
```

Generates confusion matrix (`models/confusion_matrix.png`) and training curves (`models/training_curves.png`).

### Step 5 — Plan a walking route

```bash
python plan_route.py --minutes 60 --start pushkin_monument
```

Uses OSRM public API for real walking routes. Optional flags: `--visit-minutes N` forces a fixed dwell time per stop; `--distance-matrix` prints the OSRM travel-time matrix.

Single-image CLI inference:

```bash
python predict.py path/to/photo.jpg --top 5    # --model PATH to use another .keras file
```

## Adding a new landmark

1. Add an entry to `data/landmarks.json` following the existing schema.
2. Create `data/raw/<new_id>/` and add at least 10 photos.
3. Place a thumbnail in `data/photos/<new_id>.jpg`.
4. Re-run `collect_data.py` then `train.py`.

## PWA & offline support

The app is a Progressive Web App. The service worker (`sw.js`) runs at root scope (`/`) and caches:

- **App shell** — `/app` plus precached Leaflet JS/CSS, favicon, and manifest (network-first, 3 s timeout)
- **Landmarks** — `/landmarks` (cache-first)
- **Photos** — `/photo/*` (cache-first)

### Offline predict queue

When offline, predictions are queued in `localStorage` (5-item cap). Each item stores the base64 image and status (`queued` → `processing` → `done`/`failed`). When the browser comes back online:

1. Queue items auto-process in order
2. Results appear in both the main result card and the queue panel
3. Completed items are auto-pruned on `QuotaExceeded`

### Cache versioning

The SW cache is versioned (`pushkinskaya-v3` in `sw.js`). Increment the version string to bust all caches on update. The app shell is network-first with a 3-second timeout and cache fallback, so a deploy is picked up on the next load even on a weak connection; landmarks and photos stay cache-first for offline use.

## Production deployment

### Caddy reverse proxy

The `Caddyfile` configures Caddy as a reverse proxy in front of gunicorn:

- **Auto-HTTPS** — Let's Encrypt provisioning (just point your DNS A record)
- **gzip** — compresses all responses
- **Cache-Control headers** — static assets cached 24h, API responses not cached
- **Metrics** — `/metrics` is proxied; Flask enforces `X-Metrics-Token` whenever the variable is set

For local development, Caddy listens on `:80` (plain HTTP). For production HTTPS, uncomment the domain block in `Caddyfile` and replace `your-domain.com`.

### Docker Compose

```bash
cp .env.example .env
# Edit .env for your deployment (METRICS_TOKEN is required)
docker compose up -d
```

Services:
- **caddy** — ports 80/443, reverse proxy
- **web** — port 5000 (internal), Flask + gunicorn

### Health check

The Docker container includes a health check:
```
HEALTHCHECK --interval=30s --timeout=5s --start-period=90s --retries=3
    CMD curl -f http://localhost:5000/ || exit 1
```

The `/` endpoint returns `503` when the model is missing or is a Git LFS pointer stub.

## Monitoring

### Prometheus metrics

`GET /metrics` returns Prometheus-compatible counters:

| Metric | Type | Description |
|--------|------|-------------|
| `pushkinskaya_http_requests_total` | counter | HTTP requests by endpoint and status |
| `pushkinskaya_prediction_confidence` | histogram | Prediction confidence distribution |
| `pushkinskaya_osrm_requests_total` | counter | OSRM routing requests |
| `pushkinskaya_uptime_seconds` | gauge | Process uptime |

Metrics are per-worker, in-memory. Counters reset on worker restart — suitable for container metrics shipped to Prometheus/Grafana.

When `METRICS_TOKEN` is set, scrape with the `X-Metrics-Token` header; query-string tokens are not accepted so the secret never appears in access logs. Docker Compose requires the variable and refuses to start without it, so composed deployments never expose `/metrics` unauthenticated. Running the dev server without it leaves `/metrics` open on loopback only.

## Backup & recovery

```bash
./scripts/backup.sh              # backup to /var/backups/pushkinskaya
./scripts/backup.sh /mnt/backup  # backup to custom directory
```

Backs up:
- `models/` — trained model + metadata
- `data/` — landmarks.json, photos (excludes raw/ and images/)
- `logs/` — all log files

Retains 7 days of backups. Cron example (daily at 3 AM):
```
0 3 * * * /path/to/tourist_app/scripts/backup.sh /mnt/backup >> /var/log/tourist-backup.log 2>&1
```
