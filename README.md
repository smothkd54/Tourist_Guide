# Pushkinskaya Street Tourist Guide — Landmark Recognition System

A tourist landmark identification system for Pushkinskaya Street, Rostov-on-Don, Russia.
Identification runs entirely on your machine — no cloud API. Route planning and map tiles use public OSRM/OpenStreetMap services when online.

## Quick start

### 1. Clone with Git LFS (for images and the model)

GitVerse is the primary remote. The account and repository import are still
pending, so the URL below is a placeholder — see
[`docs/gitverse.md`](docs/gitverse.md) for the import and first-push steps.

```bash
git lfs install
git clone https://gitverse.ru/<login>/Tourist_Guide.git
cd Tourist_Guide
```

The GitHub mirror is `https://github.com/smothkd54/Tourist_Guide.git`.

### 2. Install dependencies

Requires Python 3.11 or newer.

```bash
pip install -e ".[dev]"
```

This installs the package in editable mode with all training, testing, and linting dependencies.

For production/Docker (slimmer, no TensorFlow/matplotlib/pytest):
```bash
pip install -r requirements-serve.txt
```

### 3. Start PostgreSQL (recommended)

```bash
cp .env.example .env
# Fill in POSTGRES_PASSWORD, DATABASE_URL, ADMIN_TOKEN and METRICS_TOKEN.
# Generate secrets with:
#   python -c "import secrets; print(secrets.token_urlsafe(32))"
docker compose up -d db

# PowerShell:  $env:DATABASE_URL = "postgresql://pushkinskaya:<password>@127.0.0.1:5432/pushkinskaya"
# bash:        export DATABASE_URL=postgresql://pushkinskaya:<password>@127.0.0.1:5432/pushkinskaya
alembic upgrade head
python scripts/seed_db.py
```

`DATABASE_URL` is the switch: when it is set the API reads the catalogue from
PostgreSQL and stores anonymous reports and shared itineraries there. When it
is unset the API falls back to the committed JSON files, and write endpoints
return `503` — that mode exists for development and for the CI fallback run.
The composed deployment always sets `DATABASE_URL`.

### 4. Start the server

```bash
python backend/app.py
```

Open http://localhost:5000/app in your browser.

`GET /` reports which source is in use:

```json
{"status":"ok","model_loaded":true,"landmarks":46,"data_source":"postgres",
 "database":{"status":"ok","version":"16.15","latency_ms":4.5}}
```

The dev server binds to `127.0.0.1` by default (not reachable from your LAN). Set `HOST=0.0.0.0` if you explicitly want to expose it. Docker/gunicorn is unaffected and still binds `0.0.0.0`.

### CLI entry points

After `pip install -e ".[dev]"`, these commands are available:

| Command | What it does |
|---------|-------------|
| `pushkinskaya-train` | Fine-tune EfficientNetB0 |
| `pushkinskaya-evaluate` | Generate confusion matrix + metrics |
| `pushkinskaya-predict` | CLI inference on a single image |
| `pushkinskaya-collect` | Organise raw photos into train/val/test splits |
| `pushkinskaya-plan` | Generate a walking route via OSRM |
| `pushkinskaya-preflight` | Verify model + data before starting server |

### Docker

**Quick start (docker-compose):**
```bash
git lfs pull
cp .env.example .env
# Set POSTGRES_PASSWORD, ADMIN_TOKEN and METRICS_TOKEN in .env — compose
# refuses to start while any of them is empty. Generate each with:
#   python -c "import secrets; print(secrets.token_urlsafe(32))"
# Then set DATABASE_URL to the same password on 127.0.0.1:5432.
docker compose up -d --build
```

This starts:
- **db** (`postgres:16-alpine`, loopback `127.0.0.1:5432`) — catalogue, reports, itineraries
- **web** (loopback `127.0.0.1:5000`, also reachable by Caddy over the compose network) — Flask + gunicorn; the entrypoint applies migrations, seeds an empty database, runs preflight, then serves
- **caddy** (ports 80/443) — reverse proxy on plain HTTP `:80`; the HTTPS site block is commented out in `Caddyfile` until a domain points at the host

**Manual (docker run):**
```bash
git lfs pull
docker build -t pushkinskaya-explorer .
docker run -p 5000:5000 \
  -e CORS_ORIGINS=https://your-domain.com \
  -e METRICS_TOKEN=replace-with-a-long-random-value \
  -e ADMIN_TOKEN=replace-with-another-long-random-value \
  -e DATABASE_URL=postgresql://pushkinskaya:<password>@host.docker.internal:5432/pushkinskaya \
  pushkinskaya-explorer
```

Without `DATABASE_URL` the container serves the JSON catalogue (read-only mode:
`/reports`, `/itineraries` and `/admin/*` return `503`).

**Swap model without rebuild:**
```bash
python convert_tflite.py && docker compose restart web
```

**Environment variables (.env):**

| Variable | Default | Description |
|----------|---------|-------------|
| `HOST` | `127.0.0.1` | Dev server bind address (`python backend/app.py` only) |
| `CORS_ORIGINS` | `http://localhost:*\|http://127.0.0.1:*` | Pipe-delimited allowed origins (exact host, `:*` = any port; matched with anchored patterns) |
| `GUNICORN_WORKERS` | `2` | Number of gunicorn worker processes |
| `MODEL_PATH` | `/app/models/landmark_classifier.tflite` | Path to the TFLite model |

## Android app

`android/` is a native Kotlin/Compose client for the same API: Explore, Detail
(with photo credit and a "Report a problem" dialog), Identify (camera or
gallery → `POST /predict`), Routes (`POST /plan-custom`) and local reminders.

The report dialog offers four categories (wrong photo, wrong information,
closed/inaccessible, other), validates the 10–2000 character message locally,
posts to `/reports`, and shows a thank-you or a retry message. Reports are
anonymous; there is no account or login.

```bat
cd android
gradlew.bat assembleDebug
adb reverse tcp:5000 tcp:5000
adb install -r app\build\outputs\apk\debug\app-debug.apk
```

`adb reverse` maps the phone's `localhost:5000` to the PC, so the debug build
does not need a LAN IP or `HOST=0.0.0.0`. The GitHub mirror builds the APK and
runs its unit tests; launch is verified on the demo phone. The GitVerse pipeline
does not build Android because a cold Gradle build does not reliably fit the
30-minute job cap.

Route reminders use `AlarmManager`; WorkManager is used only for the 6-hour
place-status poll, where a late run is harmless.

## Photo attribution

`data/photo_attribution.json` records the author, licence, licence URL and
source page for every published thumbnail. `scripts/audit_photo_licenses.py`
rebuilds it from the Wikimedia Commons API and fails if any published photo
lacks a free licence or a credit. The API attaches the credit to each landmark
as `photo_attribution`, and both the web UI and the Android detail screen show
it under the photo.

Run the audit in CI (`.github/workflows/photo-audit.yml`), not locally:
Wikimedia is unreachable from the developer's network.

### Photo verification status

The licence audit proves every thumbnail is legally publishable; it does not
prove the thumbnail shows the landmark. The original `photo_sources.json` was
filled from one photographer's 2020 Rostov walk, and part of the assignment was
positional: three frames of a courtyard gate became three different landmarks,
and seven frames of one lion sculpture became seven different monuments.

All 46 thumbnails have since been checked against the landmark record, its
coordinates and a Commons category or Wikidata item that is specifically about
the object. 30 were re-sourced and verified; 8 were already correct.
Eight landmarks are now **text-only** because no free-licensed photo of the
actual object exists on Commons or Wikipedia:
`bakulin_house`, `budyonny_bust`, `cinema_house`, `lanterns_1904`,
`lyre_fountain`, `sorge_bust`, `vysotsky_monument`, `writers_busts`
(the Vysotsky monument photograph on ru.wikipedia is fair use, so it cannot be
republished). A missing photo is better than a wrong one: the clients hide the
image and its credit when `data/photos/<id>.jpg` is absent.

Measured effect: of the 25 published photos whose landmark is one of the 29
model classes, 11 are classified correctly and 8 clear the 0.35 threshold
(against 60% on the held-out test split). The remaining gap is the photos —
several monuments have very few training examples — and is a known limitation,
not a licensing issue.

Re-sourcing is a content task, not a code fix: each replacement has to be a
Commons file that actually depicts the landmark. Wikimedia is reachable through
the in-app browser even though it is blocked from PowerShell; `photo_sources.json`
plus the CI audit then regenerate the attribution.

| GET    | `/app`                | —                            | web UI (also `/app/`)                |
| GET    | `/app/static/<path>`  | —                            | self-hosted static assets            |
| GET    | `/favicon.ico`        | —                            | SVG favicon                          |

| GET    | `/landmarks/<id>`     | —                            | single landmark object               |
| GET    | `/nearby`             | `lat`, `lon`, `radius_m`     | landmarks within radius              |
| GET    | `/plan`               | `start`, `minutes`, `visit`  | dynamic walking route via OSRM       |
| POST   | `/plan-custom`        | `{ landmarks, start, optimize? }` | custom walking route via OSRM    |
| GET    | `/route`              | —                            | pre-planned route from `planned_route.json` |
| POST   | `/reports`            | `{ landmark_id?, category, message }` | `201` stored report; `503` when no database |
| POST   | `/itineraries`        | `{ landmarks, start, optimize? }` | `201 { id, route }` — saved shareable walk |
| GET    | `/itineraries/<id>`   | —                            | stored route, stops and `created_at` |
| GET    | `/admin/stats`        | `X-Admin-Token` header       | row counts, database size, model status |
| GET    | `/admin/reports`      | `status?`, `limit`, `offset`, token | reports, newest first          |
| PATCH  | `/admin/reports/<id>` | `{ status }`, token          | updated report status                 |
| GET    | `/photo/<id>`         | —                            | thumbnail image for a landmark       |
| GET    | `/photos/available`   | —                            | list of landmark IDs with photos     |
| POST   | `/predict`            | `{ "image": "<base64>" }`    | prediction + landmark info (10 MB max) |
| GET    | `/model/info`         | —                            | model training metadata (404 if absent) |
| GET    | `/metrics`            | —                            | Prometheus metrics (header token when configured) |
| GET    | `/sw.js`              | —                            | service worker script                |

Parameter details:
- `/nearby` — `lat`/`lon` must be finite and in range; `radius_m` is 1–50000 (default 500).
- `/plan` — `minutes` is 15–480 (default 60); `visit` is 0–120 and optional (per-landmark dwell is estimated when omitted). Limited to 30 requests/minute per client.
- `/plan-custom` — `landmarks` is a non-empty list of known landmark ID strings (duplicates are removed); `start` must be one of them; `optimize` must be a boolean.
- `/predict` — JSON body up to 10 MB; base64 or data-URI JPEG/PNG. Returns `landmark_id` (the landmark detail card to open) and `class_id` (the raw model class; they differ only for the merged `kramer_estate` class).
- `/reports` — `category` is `wrong_photo`, `wrong_info`, `closed` or `other`; `message` is 10–2000 characters; `landmark_id` is optional but must exist. Limited to 5 reports/minute per client.
- `/itineraries` — same validation as `/plan-custom`; the response `id` is a UUID used in `?itinerary=<id>`.
- `/admin/*` — `ADMIN_TOKEN` must be set (otherwise `503`); the request must carry it in `X-Admin-Token` (otherwise `401`). Report statuses are `open`, `resolved`, `dismissed`.

Health check returns `503` (not `200`) when the model is missing or is a Git LFS pointer stub. A database outage does not fail the health check while the JSON fallback is serving reads; the body then reports `data_source: "json"` and a `database_error`. If PostgreSQL was up at boot and goes away, `GET /` still answers immediately: the first failed connection arms a `DB_POOL_RETRY_SECONDS` backoff, writes return `503` in milliseconds, and the API reconnects once the backoff expires.

## Database

PostgreSQL 16 is the deployment source of truth. Images and the model stay on
disk; the database stores their metadata, the published-photo credit, anonymous
reports and shared itineraries. `DATABASE_URL` selects PostgreSQL; when it is
unset the API falls back to the committed JSON catalogue.

### Schema

Seven tables, defined by the initial Alembic migration:

| Table | Purpose |
|-------|---------|
| `landmarks` | 46 catalogue records: names (EN/RU), address, year, type, style, architect, description, fun fact, coordinates, sort order |
| `photos` | Published thumbnails and their author/licence/source. A check constraint forbids a published row without a full credit; a partial unique index allows one published photo per landmark |
| `model_classes` | 29 model classes: class index (unique), validation flag, per-split image counts, mapping note. `kramer_estate` is a merged training class and points at `kramer_mansion` |
| `itineraries` | Saved route: UUID, start landmark, mode, totals and the full route JSON |
| `itinerary_items` | Ordered stops with dwell minutes; `(itinerary_id, position)` primary key |
| `reports` | Anonymous problem reports: optional landmark, category, message, status and timestamps |
| `schema_migrations` | Alembic version table |

Indexes cover the read paths: trigram GIN on both name columns, `(lat, lon)`
for nearby queries, `(status, created_at DESC)` for the admin queue, and the
partial unique index on published photos. A trigger maintains
`landmarks.updated_at`.

### Migrations

```bash
export DATABASE_URL=postgresql://pushkinskaya:<password>@127.0.0.1:5432/pushkinskaya
alembic upgrade head        # apply
alembic downgrade -1        # revert one revision
alembic current             # show the applied revision
alembic revision -m "add ..."   # create a new revision
```

`alembic.ini` carries no credentials; `migrations/env.py` reads
`DATABASE_URL`. The container entrypoint runs `alembic upgrade head`
automatically, so a fresh volume converges before the first request.

### Seeding

```bash
python scripts/seed_db.py            # upsert everything (idempotent)
python scripts/seed_db.py --if-empty # no-op when landmarks exist (container boot)
python scripts/seed_db.py --check    # verify counts without writing
```

The script reads `landmarks.json`, `photo_attribution.json`,
`photo_sources.json`, `class_names.json` and the split manifest. It verifies
46 landmarks, 29 classes and 38 published, credited photos; a re-run converges
instead of duplicating, and photos that are no longer published are removed.

### Admin CLI

There are no user accounts. Operators use a shell on the host:

```bash
python scripts/admin.py stats
python scripts/admin.py reports --status open --limit 20
python scripts/admin.py resolve <report-id> --status resolved
```

The same operations are available over HTTP with the `X-Admin-Token` header
(`/admin/stats`, `/admin/reports`, `PATCH /admin/reports/<id>`). If
`ADMIN_TOKEN` is unset, those routes return `503`; a wrong token returns `401`.

### Backup and restore

`scripts/backup.sh` archives `models/`, `data/` and `logs/`, and adds a
`pg_dump --format=custom` when `DATABASE_URL` is set. Restore with:

```bash
DATABASE_URL=postgresql://... ./scripts/db_restore.sh /var/backups/pushkinskaya/db_20261103_030000.dump
```

`db_restore.sh` runs `pg_restore --clean --if-exists`, re-applies migrations,
then verifies the seed counts.

## Training pipeline

### Step 1 — Collect photos

Place your photos in `data/raw/<landmark_id>/`. Aim for at least 10 photos per landmark.

### Step 2 — Organise splits

```bash
python collect_data.py
```

Splits photos 80% train / 10% val / 10% test. Use `--source PATH` to read from a directory other than `data/raw`.

### Step 2b — Rebuild the dataset from the manifest

The images are not in git, but the split is. `data/images_v2/manifests/split.json`
records, for each of the 328 images, its source file, its destination path and
its sha256:

```bash
python scripts/build_dataset.py --verify          # report what exists, change nothing
python scripts/build_dataset.py                   # copy the missing files
python scripts/build_dataset.py --force           # rebuild every file
python scripts/build_dataset.py --update-manifest # rewrite sha256 values that drifted
```

Sources live in `data/images/` and `data/images_enriched/`, which are also not
committed; restore them from the project archive first. `tests/test_dataset_manifest.py`
fails CI if the manifest becomes internally inconsistent: one source photo in
two splits, a model class without training images, or a class order that no
longer matches `models/class_names.json` (Keras derives labels from directory
names, so a reordering would silently remap every prediction).

### Step 3 — Train

```bash
python train.py --epochs-head 10 --epochs-fine 20
```

Options:
```
--batch       INT   batch size (default 32)
--epochs-head INT   phase 1 epochs, head only (default 10)
--epochs-fine INT   phase 2 epochs, fine-tune (default 20)
```

Training uses EfficientNetB0 (pretrained on ImageNet) with two phases:
- **Phase 1**: classification head only (base frozen)
- **Phase 2**: top layers unfrozen, end-to-end fine-tune

After training, `models/model_metadata.json` is written with class count, accuracy, training timestamps, and hyperparameters.

### Model quality (current checkpoint)

Measured on a held-out split that no training image touches, with duplicate and
near-duplicate photos kept inside a single split:

| Metric | Value |
|---|---|
| Classes | 29 (of 46 landmarks; the rest stay browsable but are not camera-recognised) |
| Test accuracy | 60.0% (39/65) |
| Answer precision at the 0.35 threshold | 82% (94% at 0.40) |
| Coverage at 0.35 | 52% of test photos answered |

Known limitation: the classifier has no "not a landmark" class, so it will
confidently guess when pointed at something that is not a listed building. The
API returns the top 5 candidates so the user can correct it.

Two classes (`lashch_revenue_house`, `tkachenko_revenue_house`) survive only in
the training split — Wikimedia Commons has no further free-licensed photos — so
they are masked out of predictions rather than returned unvalidated.

### Step 4 — Evaluate


## PWA & offline support

The app is a Progressive Web App. The service worker (`sw.js`) runs at root scope (`/`) and caches:

- **App shell** — `/app` plus precached Leaflet JS/CSS, favicon, and manifest (network-first, 3 s timeout)
- **Landmarks** — `/landmarks` (cache-first)
- **Photos** — `/photo/*` (cache-first)

### Offline predict queue

When offline, predictions are queued in `localStorage` (5-item cap). Each item stores the base64 image and status (`queued` → `processing` → `done`/`failed`). When the browser comes back online:

1. Queue items auto-process in order
2. Results appear in both the main result card and the queue panel
3. Completed items are auto-pruned on `QuotaExceeded`

### Cache versioning

The SW cache is versioned (`pushkinskaya-v3` in `sw.js`). Increment the version string to bust all caches on update. The app shell is network-first with a 3-second timeout and cache fallback, so a deploy is picked up on the next load even on a weak connection; landmarks and photos stay cache-first for offline use.

## Production deployment

### Caddy reverse proxy

The `Caddyfile` configures Caddy as a reverse proxy in front of gunicorn:

- **Auto-HTTPS** — Let's Encrypt provisioning (just point your DNS A record)
- **gzip** — compresses all responses
- **Cache-Control headers** — static assets cached 24h, API responses not cached
- **Metrics** — `/metrics` is proxied; Flask enforces `X-Metrics-Token` whenever the variable is set

For local development, Caddy listens on `:80` (plain HTTP). For production HTTPS, uncomment the domain block in `Caddyfile` and replace `your-domain.com`.

### Docker Compose

```bash
cp .env.example .env
# Required: POSTGRES_PASSWORD, ADMIN_TOKEN, METRICS_TOKEN
# Also set DATABASE_URL to the same password on 127.0.0.1:5432.
docker compose up -d --build
```

Services:
- **db** — `postgres:16-alpine`, loopback `127.0.0.1:5432`, named volume, `pg_isready` healthcheck
- **web** — port 5000 (internal), Flask + gunicorn; starts only after the database is healthy
- **caddy** — ports 80/443, reverse proxy

The web entrypoint is idempotent on every boot: `alembic upgrade head` →
`scripts/seed_db.py --if-empty` → `preflight_check.py` → gunicorn. A fresh
volume therefore comes up with the full catalogue; an existing one is left
alone.

### Health check

The Docker container includes a health check:
```
HEALTHCHECK --interval=30s --timeout=5s --start-period=90s --retries=3
    CMD curl -f http://localhost:5000/ || exit 1
```

The `/` endpoint returns `503` when the model is missing or is a Git LFS pointer stub. It also reports `data_source` (`postgres` or `json`) and a nested `database` object, so a database problem is visible without failing a read-only fallback.

## Monitoring

### Prometheus metrics

`GET /metrics` returns Prometheus-compatible counters:

| Metric | Type | Description |
|--------|------|-------------|
| `pushkinskaya_http_requests_total` | counter | HTTP requests by endpoint and status |
| `pushkinskaya_prediction_confidence` | histogram | Prediction confidence distribution |
| `pushkinskaya_osrm_requests_total` | counter | OSRM routing requests |
| `pushkinskaya_uptime_seconds` | gauge | Process uptime |

Metrics are per-worker, in-memory. Counters reset on worker restart — suitable for container metrics shipped to Prometheus/Grafana.

When `METRICS_TOKEN` is set, scrape with the `X-Metrics-Token` header; query-string tokens are not accepted so the secret never appears in access logs. Docker Compose requires the variable and refuses to start without it, so composed deployments never expose `/metrics` unauthenticated. Running the dev server without it leaves `/metrics` open on loopback only.

## Backup & recovery

```bash
./scripts/backup.sh              # backup to /var/backups/pushkinskaya
./scripts/backup.sh /mnt/backup  # backup to custom directory
```

Backs up:
- `models/` — trained model + metadata
- `data/` — landmarks.json, photo attribution, published photos (excludes raw/ and training images)
- `logs/` — all log files
- PostgreSQL — `pg_dump --format=custom` when `DATABASE_URL` is set

Restore a database dump:

```bash
DATABASE_URL=postgresql://... ./scripts/db_restore.sh /mnt/backup/db_20261103_030000.dump
```

The restore runs `pg_restore --clean --if-exists`, re-applies migrations, then
verifies the seed counts.

Retains 7 days of backups. Cron example (daily at 3 AM):
```
0 3 * * * /path/to/tourist_app/scripts/backup.sh /mnt/backup >> /var/log/tourist-backup.log 2>&1
```

## CI/CD

GitVerse is the primary pipeline (`.gitverse/workflows/ci.yaml`):

1. **Backend** — `ruff check .`; the suite in JSON mode; PostgreSQL 16 installed
   with `apt`, migrated and seeded; the suite again in PostgreSQL mode
2. **Docker** — builds the serving image, starts it without `DATABASE_URL`,
   checks preflight, `/` (`data_source: json`) and all 46 landmarks

The GitHub mirror (`.github/workflows/ci.yml`) runs the same backend checks with
a PostgreSQL service container, and adds the jobs that do not fit GitVerse's
30-minute cap:

3. **Android build** — `assembleDebug testDebugUnitTest`, APK and test report artifacts
4. **Docker build** — image build, container smoke test, Trivy scan (fails on fixable CRITICAL/HIGH)
5. **Photo audit** (`.github/workflows/photo-audit.yml`) — re-fetches author and licence from Wikimedia, because Wikimedia is unreachable from the developer's network

The GitHub CI workflow is kept until the first green GitVerse run; after that it
can be removed except for the Android and photo-audit jobs. See
[`docs/gitverse.md`](docs/gitverse.md) for the remote setup.

## Data sources

- **Photos**: Wikimedia Commons — only free licences; author, licence, licence URL and source page are recorded in `data/photo_attribution.json` and shown with each photo. Eight landmarks are text-only because no free-licensed photo of the actual object exists.
- **Geocoding**: OpenStreetMap Nominatim (12 landmarks) and manual lookup on Yandex Maps (34 landmarks); the source is recorded per landmark as `coordinate_source`
- **Routing**: OSRM public demo server — free, no API key, rate-limited
- **Map tiles**: OpenStreetMap — free, attribution required
- **Map library**: Leaflet.js — self-hosted in `frontend/static/leaflet/`
